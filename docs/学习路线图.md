## 🥈 第二阶段：发布与订阅（第 2-3 天）

> 实现 A 项目发消息、B 项目收消息，掌握三种交换机的用法和消息确认机制。

### 2.1 Publisher（A 项目 — 控制台应用）

- [ ] 基于 `Host.CreateDefaultBuilder` + `BackgroundService` 运行（统一生命周期管理）
- [ ] 每 3 秒随机生成一条 OrderEvent 消息
- [ ] 分别通过 **Fanout / Direct / Topic** 三种交换机发送
- [ ] 发布者使用**独立 Channel**（不与消费者共享，保证线程安全）
- [ ] 启用 Publisher Confirms，注册 `BasicAcksAsync` / `BasicNacksAsync` 回调
- [ ] 开启 `mandatory: true`，注册 `BasicReturnAsync` 监听不可路由消息
- [ ] 设置 `DeliveryMode = 2`（消息持久化，Broker 重启不丢失）
- [ ] 可选：GZipStream 压缩大消息（> 4KB），header 标记 `content-encoding: gzip`

### 2.2 Subscriber（B 项目 — Worker Service）

- [ ] **FanoutConsumerWorker**：绑定 `order.fanout`，接收所有消息
- [ ] **DirectConsumerWorker**：绑定 `order.direct`，按 EventType 精确过滤
- [ ] **TopicConsumerWorker**：绑定 `order.topic`，按通配符模式匹配接收
- [ ] 每个 Worker 使用**独立 Channel**
- [ ] 设置 PrefetchCount = 10（配置可调，控制推送缓冲量）
- [ ] AutoAck = false，消费完成后手动确认
- [ ] 注册 `ConsumerCancelledAsync` 监听 Broker 取消消费者

### 2.3 消息确认机制

- [ ] 理解 Publisher Confirm 的三种模式：

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| 异步回调 | BasicAcksAsync / BasicNacksAsync 事件 | **推荐**，不阻塞发布 |
| 同步等待 | WaitForConfirmsOrThrowAsync | 低吞吐、测试 |
| 批量确认 | WaitForConfirmsOrDieAsync | 高吞吐优化 |

- [ ] 消费成功 → `basicAck` 通知 Broker 删除消息
- [ ] 消费失败 → `basicNack(requeue=false)` → 进入死信队列（不重新入队）
- [ ] 理解"队列持久化 ≠ 消息持久化"：durable 队列 + DeliveryMode=2 才保证重启不丢

### 2.4 Channel 管理规范

- [ ] 牢记：`IChannel` **不是线程安全的**，严禁多线程共享
- [ ] 发布与消费分离：使用不同的 Channel
- [ ] 每个 Consumer 使用独立的 Channel
- [ ] 连接恢复后需重新注册 Consumer 和回调

## 🥉 第三阶段：高级特性（第 4-5 天）

> 掌握死信队列、幂等消费、有限重试、备用交换机，让 Demo 具备生产级质量。

### 3.1 死信队列（DLQ）

- [ ] 理解 requeue=true 的危害：无限循环 / 日志爆炸 / 无法追踪 / 无法干预
- [ ] 死信交换机（DLX）：`dlx.order`（Fanout 类型）
- [ ] 死信队列（DLQ）：`order.dlq`
- [ ] 主队列声明时配置 `x-dead-letter-exchange=dlx.order`
- [ ] 理解死信产生的 4 种条件：

| 触发条件 | 说明 |
|----------|------|
| basicNack(requeue=false) | 业务处理异常（本 Demo 聚焦） |
| basicReject(requeue=false) | 消息格式错误 |
| x-message-ttl 过期 | 超时未消费（暂不启用） |
| x-max-length 队列满 | 队列积压上限（暂不启用） |

- [ ] 死信消息自动附加的 Headers：

| Header | 含义 | 示例 |
|--------|------|------|
| x-first-death-exchange | 首次死亡的交换机 | order.direct |
| x-first-death-queue | 首次死亡的队列 | order.created.q |
| x-first-death-reason | 死亡原因 | rejected |
| x-death | 完整死亡历史（数组） | [{reason, queue, time}, ...] |

- [ ] 管理控制台查看死信消息内容及 x-death 头

### 3.2 有限重试策略

- [ ] 理解为什么不能用 RabbitMQ requeue 做重试：无退避间隔、消费端无感知、无法区分异常类型
- [ ] 使用 Polly `ResiliencePipeline` 在消费者内部实现重试：

```
第 1 次失败 → 等待 1s → 第 2 次失败 → 等待 3s → 第 3 次失败 → basicNack → DLQ
```

- [ ] 配置项：MaxRetryCount=3 / BaseDelaySeconds=1 / MaxDelaySeconds=30
- [ ] 启用抖动（Jitter）避免惊群
- [ ] 定义 `UnrecoverableMessageException`：不可重试的异常直接入 DLQ

### 3.3 备用交换机（AE — Alternate Exchange）

- [ ] 理解 AE 与 DLQ 的区别：

| 特性 | DLQ | AE |
|------|-----|----|
| 处理场景 | **消费失败**的消息 | **路由失败**的消息 |
| 触发时机 | basicNack/basicReject | mandatory 无绑定匹配 |
| 配置位置 | 队列的 x-dead-letter-exchange | 交换机的 alternate-exchange |

- [ ] 适用场景：新增 EventType 忘绑定 / 路由键拼写错误 / 运维误删队列
- [ ] 业务交换机声明时设置 `alternate-exchange=order.unrouted.ae`
- [ ] AE 行为特征：仅路由失败、消息原封不动、可与 DLQ 共存

### 3.4 幂等消费（防重复消费）

- [ ] RabbitMQ 投递保证是 "At least once"，以下场景会产生重复消息：

| 场景 | 说明 |
|------|------|
| Ack 前宕机 | 消费者处理完但未发 Ack 就挂了 |
| 网络闪断 | Ack 未到达 Broker，超时重投 |
| 自动重连 | 恢复机制重新投递未确认消息 |
| Publisher 重试 | 发布者未收到确认就重试发送 |

- [ ] 消息信封 `MessageEnvelope` 携带全局唯一 `MessageId`
- [ ] 定义 `IIdempotencyChecker` 接口：`IsProcessedAsync` / `MarkAsProcessedAsync`
- [ ] 实现 `InMemoryIdempotencyChecker`（ConcurrentDictionary 存储）
- [ ] 消费者处理流程：

```
收到消息 → 检查 MessageId 已处理? → 是 → 直接 Ack 丢弃
                                   → 否 → 执行业务 → 标记已处理 → Ack
```

- [ ] 生产替换方案：Redis（SET EX 86400）/ 数据库去重表（唯一索引）

### 3.5 错误处理全景

| 异常场景 | 处理方式 |
|---------|---------|
| 连接失败 | Polly 指数退避重连，最多 5 次（1s→2s→4s→8s→16s） |
| 消费异常 | 内部 Polly 重试 3 次 → 耗尽 → basicNack(requeue=false) → DLQ |
| 不可恢复异常 | 不重试，直接 basicNack → DLQ |
| 路由失败 | mandatory=true + BasicReturn 回调 + AE 兜底 |
| 消费者被取消 | ConsumerCancelledAsync 事件记录告警 |
| 服务退出 | CancellationToken 驱动，等待当前消息处理完再退出 |

> 补全可观测性和安全能力，让 Demo 真正具备生产级品质。

### 4.1 分布式追踪（OpenTelemetry）

- [ ] 理解分布式追踪的价值：消息跨进程形成完整调用链
- [ ] W3C TraceContext 规范：

```
traceparent = "版本-trace_id-span_id-flags"
                  00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
                     └────── trace_id（全局唯一，跨进程共享）────┘  └─ span_id ─┘
```

- [ ] RabbitMQ.Client 7.x 内置 `ActivitySource("RabbitMQ.Client")`，自动追踪连接/通道/发布操作
- [ ] 自定义 ActivitySource：`RabbitMQDemo.Publisher` / `RabbitMQDemo.Subscriber`
- [ ] **Publisher 发送时注入 TraceContext**：

```
创建 Span → 将 traceparent/tracestate 写入消息 Headers → Publish
```

- [ ] **Consumer 消费时提取 TraceContext**：

```
从消息 Headers 读取 traceparent → 恢复父 Span 上下文 → 创建子 Span → 处理 → Span.End
```

- [ ] Span Tags：message.id / exchange / routing_key / queue
- [ ] 配置 OpenTelemetry SDK：

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddSource("RabbitMQDemo.Publisher", "RabbitMQ.Client")
        .AddConsoleExporter()
        // 生产环境: .AddOtlpExporter() → Jaeger/Zipkin
    );
```

- [ ] 验证：Publisher 和 Subscriber 输出相同的 `trace_id`

### 4.2 日志设计

- [ ] `ILogger<T>` 结构化日志输出
- [ ] 日志 Scope 包含 CorrelationId 用于链路追踪
- [ ] 关键日志节点：连接建立/断开 / 发送成功/失败 / 消费成功/失败 / 重试触发 / 优雅关闭

### 4.3 健康检查

- [ ] `RabbitMQHealthCheck`（IHealthCheck）：检测连接状态（Open / Closed）

### 4.4 安全与配置分离

- [ ] 区分开发环境和生产环境配置：

| 维度 | 开发环境 | 生产环境 |

### 4.5 生产级队列类型

- [ ] **Classic Queue**：默认类型，单节点（本 Demo 使用，兼容性最好）

## 📚 第六阶段：扩展知识（了解即可）

> 这些是 RabbitMQ 的进阶特性，遇到实际场景时再深入。

### 6.1 进阶特性

- [ ] **Headers Exchange**：第四种交换机，按消息元数据路由，`x-match=all/any`
- [ ] **Single Active Consumer**：单一活跃消费者，严格消息顺序，其他实例作备用
- [ ] **Consumer Priority**：高优先级消费者优先分配消息
- [ ] **消息 TTL**：队列级 `x-message-ttl` vs 消息级 `BasicProperties.Expiration`
- [ ] **优先级队列**：`x-max-priority` 参数，队列内消息排序（建议不超过 10 级）
- [ ] **批量发布**：N 条连续发布后一次确认，吞吐量可提升 3-10 倍
- [ ] **消息大小限制**：默认 128MB，生产建议不超过 1MB

### 6.2 运维与监控

- [ ] **Flow Control**：Broker 内存/磁盘达阈值时自动限流发布者
- [ ] **管理 REST API**：`GET /api/queues` / `GET /api/connections` 等 HTTP 端点
- [ ] **Firehose / Trace 插件**：调试消息路由（`rabbitmqctl trace_on`，生产慎用）

### 6.3 架构概念

- [ ] **竞争消费**（默认）：多个消费者平分消息，高吞吐但全局无序
- [ ] **顺序保证**：单 Channel 内部有序 / 多实例全局无序 / 聚合根路由策略
- [ ] **队列持久化 ≠ 消息持久化**：durable + DeliveryMode=2 才真正不丢
- [ ] **mandatory + Return** vs **Alternate Exchange**：两种路由失败处理机制对比
