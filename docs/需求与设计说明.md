# RabbitMQ .NET 10 Demo — 需求与设计说明

> 项目：e:\Demo\boke\rabbitmq-dotnet10-demo

## 一、项目概述

在空项目中创建一个生产级的 .NET 10 + RabbitMQ 发布/订阅（Pub/Sub）示例 Demo。

- **A 项目（Publisher）**：控制台应用，负责发布消息
- **B 项目（Subscriber）**：Worker Service 后台服务，负责消费消息
- 两个项目均连接到**本地 Windows 上部署的同一 RabbitMQ 服务**进行消息投递
- 既是学习 RabbitMQ 消息队列的参考，也可作为实际项目的脚手架模板

## 二、前置环境准备

运行本 Demo 前需要在本地 Windows 上安装 RabbitMQ 服务。

RabbitMQ 运行依赖 Erlang 运行时，**必须先安装 Erlang**。

- 下载地址：[https://www.erlang.org/downloads](https://www.erlang.org/downloads)
- 选择 **Windows 64-bit Installer**（推荐 OTP 26.x 或 27.x 最新版）

- 下载地址：[https://www.rabbitmq.com/docs/install-windows](https://www.rabbitmq.com/docs/install-windows)

- 安装后启用管理插件（可视化管理界面，**推荐**）：
  ```bash
  rabbitmq-plugins enable rabbitmq_management
  ```
- 启动服务（如未自动启动）：
  ```bash
  rabbitmq-service start
  ```

## 六、交换机设计（四种模式）

展示 RabbitMQ 的四种核心交换机类型：

| 交换机名称 | 类型 | 路由机制 | 用途说明 |
|------------|------|----------|----------|
| `order.fanout` | **Fanout** | 忽略路由键，广播到所有绑定队列 | 所有消费者都能收到每条消息 |
| `order.direct` | **Direct** | 路由键**精确匹配** | Created → queue_created，Paid → queue_paid |
| `order.topic`  | **Topic** | 路由键**模式匹配**（通配符） | `order.*` 匹配所有订单事件 |
| — | **Headers** | 消息 Headers 属性匹配（key-value） | 根据消息元数据路由（如 `content-type: json`），本 Demo 暂不实现，作为扩展类型说明 |

> **关于第四种 Headers Exchange**：Headers Exchange 不依赖路由键，而是根据消息的 `BasicProperties.Headers` 中的 key-value 匹配规则进行路由。当绑定时指定 `x-match=all`（所有键匹配）或 `x-match=any`（任一键匹配）决定分发目标。本 Demo 重点展示前三种最常用的类型，Headers Exchange 作为扩展知识点记录。

### 消息路由示意

```
                    ┌─→ FanoutConsumer ── 收到所有消息
                    │
Publisher ─────┬──→ DirectConsumer ──── 只收特定 EventType
               │
               └──→ TopicConsumer ───── 按模式匹配收消息
```

### 7.2 连接管理（弹性）

- **长连接**：使用 `IConnection` 长连接，避免频繁创建销毁
- **自动重连**：基于 RabbitMQ.Client 内置的 `AutomaticRecoveryEnabled`
- **重试策略**：Polly 指数退避（初始 1s → 最大 30s，最多 5 次）
- **状态监听**：连接阻塞/解除阻塞/关闭事件回调
- **优雅关闭**：`CancellationToken` + `IAsyncDisposable`，应用退出时干净释放
- **连接命名**：通过 `ClientProvidedName` 为连接命名，方便在管理控制台识别

#### Channel 最佳实践

> **Channel 与线程安全**：RabbitMQ.Client 的 `IChannel` 实例**不是线程安全的**，严禁在多线程间共享同一个 Channel。

| 原则 | 说明 |
|------|------|
| **发布与消费分离** | Publisher 使用独立 Channel，Consumer 使用独立 Channel，互不干扰 |
| **每个 Consumer 独立 Channel** | 一个 Consumer 的异常不会影响其他 Consumer |
| **长期 vs 临时 Channel** | 长生命周期的 Channel 复用，短生命周期操作（如声明临时队列）使用短暂 Channel |
| **连接恢复后重建 Channel** | `AutomaticRecoveryEnabled` 会自动重建 Channel，但需重新注册 Consumer 和 Callback |
| **每个 Channel 的并发度** | 一个 Channel 上的 Consumer 保证顺序，如需并发消费同一队列，开多个 Channel（竞争消费模式） |

```csharp
// 正确：发布和消费使用不同的 Channel
public class RabbitMQService
{
    private readonly IConnection _connection;
    private readonly IChannel _publishChannel;    // 发布专用
    private readonly IChannel _consumeChannel;    // 消费专用

    public async Task InitializeAsync()
    {
        _publishChannel = await _connection.CreateChannelAsync();
        _consumeChannel = await _connection.CreateChannelAsync();
        // 各自注册不同的回调
        await _publishChannel.ConfirmSelectAsync();
        await _consumeChannel.BasicQosAsync(0, prefetchCount: 10, global: false);
    }
}
```

#### 生产级队列类型选择

| 队列类型 | 适用场景 | 说明 |
|---------|---------|------|
| **Classic Queue** | 开发/测试、低持久性要求 | 默认类型，单节点，简单高效 |
| **Quorum Queue**（推荐生产） | 生产环境、高可用要求 | **本 Demo 推荐的生产级选择**。基于 Raft 共识算法，支持数据一致性和自动故障转移，替代旧的镜像队列（Mirrored Queue） |
| **Stream Queue** | 日志、事件溯源、消息重放 | 追加写入，支持从任意位置消费，适合大吞吐量场景（本 Demo 暂不涉及） |

**Quorum Queue 声明示例：**
```csharp
var args = new Dictionary<string, object?>
{
    { "x-queue-type", "quorum" },                     // 指定 Quorum 类型
    { "x-quorum-initial-group-size", 3 },              // 初始集群节点数
    { "x-dead-letter-exchange", "dlx.order" }          // 仍然可以绑定死信
};
await channel.QueueDeclareAsync("order.created.q", durable: true,
    exclusive: false, autoDelete: false, arguments: args);
```

> **本 Demo 默认使用 Classic Queue 以保持环境兼容性**（本地单节点无需 Raft），但在文档和生产配置中记录 Quorum Queue 作为生产首选。

### 7.3 消息确认与路由安全

#### 发布确认（Publisher Confirms）

每条消息发布后等待 Broker 确认，确保消息已到达服务端：

- **异步回调模式（推荐）**：注册 `ChannelBasicAckAsync` 和 `ChannelBasicNackAsync` 事件，异步处理确认结果
- **同步等待模式**：`WaitForConfirmsOrThrowAsync(TimeSpan)`，适合低吞吐场景
- **批量确认**：`WaitForConfirmsOrDieAsync` 等待直到上一个未确认批次完成（高吞吐优化）

```csharp
// 异步回调模式（推荐）
channel.BasicAcksAsync += (sender, args) =>
{
    logger.LogInformation("消息 {DeliveryTag} 已确认", args.DeliveryTag);
    return Task.CompletedTask;
};
channel.BasicNacksAsync += (sender, args) =>
{
    logger.LogWarning("消息 {DeliveryTag} 未被确认", args.DeliveryTag);
    return Task.CompletedTask;
};
```

#### 消费确认（Consumer Ack/Nack）

- 消费成功 → `basicAck` 通知 Broker 删除消息
- 消费失败 → `basicNack(requeue=false)` → 消息进入**死信交换机（DLX）**，投递到死信队列存储，不再重新入队主队列

#### 消息持久化（DeliveryMode）

**队列持久化 ≠ 消息持久化**。即使队列声明为 `durable: true`，消息默认是**非持久化**的（DeliveryMode=1），Broker 重启后丢失。

| 级别 | DeliveryMode | 行为 | 推荐场景 |
|------|-------------|------|---------|
| 非持久化 | 1 | Broker 重启后消息丢失 | 日志、通知、缓存刷新（丢了也无所谓） |
| 持久化 | 2 | Broker 重启后消息恢复 | 订单、支付、业务核心数据 |

```csharp
// 持久化消息
var props = new BasicProperties
{
    DeliveryMode = DeliveryModes.Persistent  // DeliveryMode = 2
};
```

#### Mandatory 标志 + Return Listener（不可路由消息处理）

当消息发往交换机但无匹配队列时：

- `mandatory: false`（默认）→ Broker **静默丢弃**消息
- `mandatory: true` → Broker 回调 `BasicReturnAsync`，通知发布者消息未被路由

```csharp
// 注册 Return 回调
channel.BasicReturnAsync += (sender, args) =>
{
    logger.LogError("消息不可路由！Exchange: {Ex}, RoutingKey: {Rk}, ReplyCode: {Code}",
        args.Exchange, args.RoutingKey, args.ReplyCode);
    // 可将不可路由的消息记录到日志或投递到备用队列
    return Task.CompletedTask;
};

// 发布时设置 mandatory
await channel.BasicPublishAsync(
    exchange: exchange,
    routingKey: routingKey,
    mandatory: true,        // ← 必须有绑定，否则触发 Return
    basicProperties: props,
    body: body);
```

**建议**：发布者始终开启 `mandatory: true`，至少在开发/测试阶段捕获路由配置错误。

### 7.4 A 项目 — Publisher（发布者）

基于 `Host.CreateDefaultBuilder` + `BackgroundService` 的后台服务，与 Subscriber 风格一致：

| 功能 | 说明 |
|------|------|
| 运行方式 | `BackgroundService` 后台服务，由 Host 生命周期管理，支持优雅关闭 |
| 发送频率 | `Timer` / 循环，每 3 秒生成一条随机 OrderEvent |
| 发送策略 | 分别通过 **Fanout / Direct / Topic** 三种交换机发送 |
| 确认机制 | 启用 Publisher Confirms + WaitForConfirmsOrThrowAsync，确保消息到达 Broker |
| 日志 | 记录每条消息的发送状态、交换机、路由键、MessageId |
| 消息压缩 | 可选启用 `GZipStream` 压缩大消息（消息体 > 4KB 时），通过 header `content-encoding: gzip` 标记，消费者自动解压 |
| 配置 | 通过 appsettings.json 读取 RabbitMQ 连接信息 |

### 7.5 B 项目 — Subscriber（订阅者）

基于 `Worker Service` 模板，内含三个后台 Worker：

| Worker | 订阅交换机 | 行为 |
|--------|-----------|------|
| FanoutConsumerWorker | `order.fanout` | 接收所有订单消息（广播） |
| DirectConsumerWorker | `order.direct` | 按 EventType 精确过滤（如只收 "Created" 事件） |
| TopicConsumerWorker | `order.topic` | 按路由键模式匹配（如 `order.*`） |

每个 Worker 作为独立的后台服务运行，可同时启动。

#### 并发消费模型

| 维度 | 设计 | 说明 |
|------|------|------|
| **单 Worker 并发度** | 单线程顺序消费 + `BasicAck` 逐条确认 | 保证同一队列内消息的顺序性。RabbitMQ 单 Channel 的 EventConsumer 本质串行，如需并发需开多个 Channel/消费者实例 |
| **PrefetchCount** | 10（通过配置可调） | Broker 每次推送 10 条到消费者本地缓冲，减少网络往返 |
| **有序性保证** | 同一个 Queue 的多个消费者实例采用 **竞争消费** 模式 | 各取所需，RabbitMQ 轮转分发。如需严格有序，则应确保某个 OrderId 的所有事件路由到同一个 Queue（如一致性哈希交换机或 Direct 精确匹配） |
| **AutoAck** | false | 消费完成后手动 Ack，确保消息不丢失 |
| **并发安全** | `InMemoryIdempotencyChecker` 使用 `ConcurrentDictionary` | 支持多线程并发读写 |

> **消息顺序说明**：RabbitMQ 保证单个消费者在单 Channel 上接收消息的顺序。如果启动多个消费者实例绑定同一队列，则每个实例各自获取一部分消息（Round-Robin 分发），全局顺序不再保证。需要严格顺序的业务（如订单状态机）应将同一聚合根的消息路由到同一队列。

### 7.6 死信队列设计（DLQ）

#### 7.6.1 为什么需要死信队列

如果消费失败时简单地将消息重新入队（`requeue=true`），会导致：

| 问题 | 后果 |
|------|------|
| 无限循环重试 | 一条坏消息反复入队，阻塞正常消息消费 |
| 日志爆炸 | 每次重试都产生错误日志，难以聚焦真正的问题 |
| 无法追踪 | 无法区分"第一次消费"和"第 N 次重试" |
| 无法人工干预 | 运维人员看不到失败消息的内容和原因 |

引入死信队列后，消费失败的消息**不再重新入队主队列**，而是投递到单独的死信队列中存储，供开发/运维人员排查。

#### 7.6.3 核心组件

| 组件 | 名称 | 说明 |
|------|------|------|
| **死信交换机（DLX）** | `dlx.order` | Fanout 类型，所有主队列共享一个 DLX。消费失败的消息自动路由到这里 |
| **死信队列（DLQ）** | `order.dlq` | 绑定到 `dlx.order`，存储所有消费失败的消息 |
| **主队列配置** | 各主队列声明时指定 `x-dead-letter-exchange=dlx.order` | 将消费失败/拒收的消息自动投递到 DLX |

#### 7.6.4 死信产生的条件

以下情况的消息会被投递到 DLQ：

| 触发条件 | 对应场景 |
|----------|----------|
| **消费者 basicNack(requeue=false)** | 业务处理异常，主动拒绝 |
| **消费者 basicReject(requeue=false)** | 消息格式错误，直接拒绝 |
| **消息 TTL 过期（x-message-ttl）** | 消息在队列中存活超时未被消费（演示中暂不启用） |
| **队列达到最大长度（x-max-length）** | 队列积压超出上限（演示中暂不启用） |

> 本 Demo 重点关注第 1 种情况：**消费异常时 basicNack 触发死信**。

#### 7.6.5 死信消息中的附加信息

消息进入死信队列时，RabbitMQ 会自动添加以下 headers，用于排查问题：

| Header | 说明 | 示例值 |
|--------|------|--------|
| `x-first-death-exchange` | 首次死亡的交换机 | `order.direct` |
| `x-first-death-queue` | 首次死亡的队列 | `order.created.q` |
| `x-first-death-reason` | 死亡原因 | `rejected` |
| `x-death` | 完整死亡历史（数组，含时间戳） | `[{reason, queue, time, ...}]` |

#### 7.6.7 重试策略设计（消费者内部 Polly 有限重试）

##### 为什么不要依赖 RabbitMQ requeue

使用 `basicNack(requeue=true)` 让 RabbitMQ 重新入队存在以下问题：

| 问题 | 说明 |
|------|------|
| 立即重试 | 消息瞬间回到队列头部，可能被同一消费者再次消费，形成**忙等死循环** |
| 无退避间隔 | 无法控制重试间隔，每次失败 → 入队 → 立即重新投递，网络和磁盘压力大 |
| 消费端无感知 | 消费者无状态视图，不知道当前消息是"第 1 次"还是"第 N 次"消费 |
| 无法区分"可重试"与"不可重试" | 消息格式错误（如 JSON 解析失败）重试一万次也不会成功，应在第 1 次就进入 DLQ |

##### 方案：消费者内部 Polly 重试管道

在 `MessageProcessor` 中集成 Polly 重试，**不依赖 RabbitMQ 的 requeue**：

```
                               ┌──────────────────────────────┐
                               │     MessageProcessor          │
                               │                               │
  broker deliver               │  1. 幂等检查                   │
  ──────────→                  │  2. Polly 重试管道             │
                               │     ├─ 第 1 次执行业务         │
                               │     │  └─ 失败 → 等待 1s      │
                               │     ├─ 第 2 次执行业务         │
                               │     │  └─ 失败 → 等待 3s      │
                               │     ├─ 第 3 次执行业务         │
                               │     │  └─ 失败 → 抛出异常      │
                               │  3. 全部重试耗尽 → basicNack   │
                               │     (requeue=false) → DLQ      │
                               └──────────────────────────────┘
```

**配置项（扩展 `RabbitMQOptions.Consumer`）：**

```json
{
  "RabbitMQ": {
    "Consumer": {
      "PrefetchCount": 10,
      "AutoAck": false,
      "MaxConcurrentMessages": 1,
      "Retry": {
        "Enabled": true,
        "MaxRetryCount": 3,
        "BaseDelaySeconds": 1,
        "MaxDelaySeconds": 30
      }
    }
  }
}
```

**实现伪代码：**

```csharp
public class MessageProcessor
{
    private readonly IIdempotencyChecker _idempotencyChecker;
    private readonly ResiliencePipeline _retryPipeline;

    public MessageProcessor(IOptions<RabbitMQOptions> options)
    {
        var retryOptions = options.Value.Consumer.Retry;
        _retryPipeline = new ResiliencePipelineBuilder()
            .AddRetry(new RetryStrategyOptions
            {
                MaxRetryAttempts = retryOptions.MaxRetryCount,
                Delay = TimeSpan.FromSeconds(retryOptions.BaseDelaySeconds),
                BackoffType = DelayBackoffType.Exponential,
                UseJitter = true,           // 随机抖动，避免惊群
                OnRetry = args =>
                {
                    logger.LogWarning("消息处理失败，第 {Attempt}/{Max} 次重试...",
                        args.AttemptNumber, retryOptions.MaxRetryCount);
                    return default;
                }
            })
            .Build();
    }

    public async Task ProcessAsync(MessageEnvelope<OrderEvent> envelope, CancellationToken ct)
    {
        // Step 1: 幂等检查
        if (await _idempotencyChecker.IsProcessedAsync(envelope.MessageId))
        {
            logger.LogInformation("消息 {MessageId} 已处理过，跳过", envelope.MessageId);
            return;
        }

        // Step 2: Polly 有限重试（最多 3 次，指数退避 + 抖动）
        await _retryPipeline.ExecuteAsync(
            async token => await HandleBusinessAsync(envelope.Body, token), ct);

        // Step 3: 标记已处理
        await _idempotencyChecker.MarkAsProcessedAsync(envelope.MessageId);
    }
}
```

**可重试 vs 不可重试的异常区分：**

```csharp
// 不可重试的异常 — 立即进入 DLQ，不浪费重试次数
public class UnrecoverableMessageException : Exception
{
    // 如：JSON 反序列化失败、消息格式不符合预期
}

// 在 Processor 中
try
{
    await _retryPipeline.ExecuteAsync(...);
}
catch (UnrecoverableMessageException)
{
    logger.LogError("不可恢复错误，直接进入死信队列");
    throw;  // 外层 basicNack(requeue=false) → DLQ
}
catch (Exception)
{
    // 重试耗尽后进入 DLQ
    throw;
}
```

#### 7.6.9 备用交换机（AE — Alternate Exchange）

##### 备用交换机的作用

与死信队列处理**消费失败**的消息不同，备用交换机处理**路由失败**的消息：

```
Publisher → order.direct (业务交换机)
              ↓ routingKey = "UnknownKey"  → 没有任何队列匹配
              ↓
              ↓ [可选] 如果设置了 AE
              ↓
           order.unrouted.ae (备用交换机)
              ↓
           unrouted.queue (备用队列)
              ↓
           可监控/告警：有消息进入说明路由配置有误
```

##### 适用场景

| 场景 | 没有 AE 的后果 | 有 AE 的安全保障 |
|------|---------------|-----------------|
| 新增 EventType 但忘记绑定队列 | 消息静默丢失 | 流入备用队列，触发告警 |
| 代码中拼写路由键错误 | 消息静默丢失 | 可在备用队列中排查失败的 payload |
| 运维删除队列但未解绑 | 消息静默丢失 | 备用队列捕获所有不可路由消息 |

##### 声明方式

在 Exchange 声明时指定备用交换机作为参数：

```csharp
// 1. 先声明备用交换机（Fanout 类型，与 DLX 类似）
await channel.ExchangeDeclareAsync("order.unrouted.ae", ExchangeType.Fanout, durable: true);

// 2. 声明备用队列
await channel.QueueDeclareAsync("order.unrouted.q", durable: true, exclusive: false, autoDelete: false);

// 3. 绑定
await channel.QueueBindAsync("order.unrouted.q", "order.unrouted.ae", routingKey: "");

// 4. 声明业务交换机时指定 AE
var exchangeArgs = new Dictionary<string, object?>
{
    { "alternate-exchange", "order.unrouted.ae" }
};
await channel.ExchangeDeclareAsync("order.direct", ExchangeType.Direct,
    durable: true, arguments: exchangeArgs);
```

##### 备用交换机的行为特征

| 特性 | 说明 |
|------|------|
| **仅处理路由失败** | 消息成功路由到至少一个队列时，即使消费失败（那属于 DLQ 范畴），也不会进入 AE |
| **消息原封不动** | 进入 AE 的消息内容和属性与原始发布完全一致，不会被 Broker 修改 |
| **可与 DLQ 共存** | AE 和 DLQ 是两条独立的链路，分别处理"路由失败"和"消费失败" |
| **可级联** | 备用交换机本身也可以有备用交换机，但建议不超过一层避免链路混乱 |

### 7.7 幂等消费设计（防重复消费）

#### 7.7.1 为什么需要幂等消费

RabbitMQ 的消息投递保证是 **"At least once"（至少一次）**，而非"Exactly once"（精确一次）。这意味着以下场景可能导致**同一条消息被多次消费**：

| 场景 | 说明 |
|------|------|
| 消费者在处理完后、发送 Ack 前宕机 | RabbitMQ 认为消息未被消费，重新投递给其他消费者 |
| 网络闪断导致 Ack 未到达 Broker | Broker 超时后重新投递消息 |
| 消费者自动重连期间消息重复投递 | RabbitMQ 的自动恢复机制可能重复投递尚未确认的消息 |
| Publisher 重试发送 | 发布者未收到确认进行重试，导致同一条消息发送多次 |

**没有幂等处理带来的后果：**

```
订单创建事件被消费两次
  → 第 1 次：创建订单成功（正常）
  → 第 2 次：再次创建同一个订单（报错"订单已存在"或创建了重复订单）
```

#### 7.7.2 设计思路

采用 **"去重表"模式**：每条消息携带全局唯一的 `MessageId`，消费者在处理前先检查该 ID 是否已被处理过。

```
┌─────────────┐
│  Publisher  │  每条消息生成 MessageId = Guid.NewGuid()
└──────┬──────┘
       │  Message { MessageId: "abc-123", Body: OrderEvent }
       ▼
┌──────────────────────────────────────┐
│          RabbitMQ Broker             │
│  （可能重复投递同一条消息）           │
└──────────────────────────────────────┘
       │
       ▼  （可能收到 2 次相同的 MessageId）
┌──────────────────────────────────────┐
│           Consumer                   │
│                                      │
│  1. 检查 MessageId 是否已处理 ──→ 已处理 → 直接 Ack，丢弃
│  2. 未处理 → 执行业务逻辑            │
│  3. 记录 MessageId 为已处理           │
│  4. 发送 Ack                          │
└──────────────────────────────────────┘
```

#### 7.7.3 消息信封设计

在原 `OrderEvent` 外层增加消息信封（Envelope），携带全局唯一 ID：

```csharp
public class MessageEnvelope<T>
{
    /// <summary>全局唯一消息 ID，用于幂等去重</summary>
    public string MessageId { get; set; } = Guid.NewGuid().ToString("N");

    /// <summary>消息版本号，用于向后兼容</summary>
    public string Version { get; set; } = "1.0";

    /// <summary>消息创建时间戳</summary>
    public DateTime Timestamp { get; set; } = DateTime.UtcNow;

    /// <summary>消息来源（发布者标识）</summary>
    public string Source { get; set; }

    /// <summary>消息业务体</summary>
    public T Body { get; set; }
}
```

发布者每次发送消息时自动生成 `MessageId`，消费者据此进行去重判断。

> **版本兼容说明**：`MessageEnvelope` 预留了 `Version` 字段（默认为 `"1.0"`），在后续消息结构变更时用于区分版本。消费者反序列化时使用 `JsonSerializerOptions { UnmappedMemberHandling = JsonUnmappedMemberHandling.Skip }`，确保新增字段不会导致旧消费者报错，实现向前兼容。

#### 7.7.4 幂等检查接口

```csharp
public interface IIdempotencyChecker
{
    /// <summary>检查消息是否已被处理过</summary>
    Task<bool> IsProcessedAsync(string messageId);

    /// <summary>标记消息为已处理</summary>
    Task MarkAsProcessedAsync(string messageId);
}
```

#### 7.7.5 默认实现：内存去重

Demo 中提供基于 `ConcurrentDictionary` 的内存实现，服务重启后去重记录丢失（适合演示和学习）：

```csharp
public class InMemoryIdempotencyChecker : IIdempotencyChecker
{
    private readonly ConcurrentDictionary<string, byte> _processed = new();

    public Task<bool> IsProcessedAsync(string messageId)
        => Task.FromResult(_processed.ContainsKey(messageId));

    public Task MarkAsProcessedAsync(string messageId)
    {
        _processed.TryAdd(messageId, 0);
        return Task.CompletedTask;
    }
}
```

> **生产环境替换方案**：
> - **Redis**：`SET messageId processed EX 86400`（设置过期时间，自动清理）
> - **数据库**：建去重表 `message_deduplication(message_id, processed_at)`，唯一索引约束
> - 只需实现 `IIdempotencyChecker` 接口即可无缝替换

#### 7.7.6 消费者中的集成

在 `MessageProcessor` 处理管道中嵌入幂等检查：

```csharp
public class MessageProcessor
{
    private readonly IIdempotencyChecker _idempotencyChecker;
    private readonly ILogger<MessageProcessor> _logger;

    public async Task ProcessAsync(MessageEnvelope<OrderEvent> envelope)
    {
        // Step 1: 幂等检查 — 已处理过的消息直接 Ack 丢弃
        if (await _idempotencyChecker.IsProcessedAsync(envelope.MessageId))
        {
            _logger.LogInformation("消息 {MessageId} 已处理过，跳过", envelope.MessageId);
            return; // 外层调用 Ack
        }

        // Step 2: 执行业务逻辑
        await HandleBusinessAsync(envelope.Body);

        // Step 3: 标记为已处理
        await _idempotencyChecker.MarkAsProcessedAsync(envelope.MessageId);

        // Step 4: 外层调用 Ack
    }
}
```

#### 7.7.7 整体处理流程

```
收到消息
  │
  ▼
反序列化 → MessageEnvelope<OrderEvent>
  │
  ▼
┌─ 检查：MessageId 是否已处理？ ──→ 已处理 ──→ basicAck → 结束
│    (未处理)
▼
执行消息处理逻辑
  │
  ▼
标记 MessageId 为已处理
  │
  ▼
basicAck → 结束
```

### 7.8 错误处理

| 场景 | 处理方式 |
|------|----------|
| 连接失败 | Polly 指数退避重试，最多 5 次（初始 1s，每次 ×2，最大 30s） |
| 消息消费异常 | 消费者内部有限重试：最多 3 次 → 仍失败 → `basicNack(requeue=false)` → 进入死信队列 |
| 死信消息 | 存储在 DLQ 中，记录死信原因（原始异常 + 重试次数），可供管理控制台查看 |
| 服务退出 | `CancellationToken` 驱动，等待当前消息处理完成再退出 |

### 7.9 分布式追踪（OpenTelemetry + W3C TraceContext）

#### 7.9.1 为什么需要分布式追踪

在发布/订阅模型中，消息跨进程流动，传统单体日志难以串联完整链路：

```
Publisher (进程 A)                       Subscriber (进程 B)
────────────────────                    ────────────────────
发送消息 ──────────────────────────→    收到消息
  │                                       │
  LOG: "发送成功" ← 有 trace_id           LOG: "处理失败" ← 有另一个 trace_id
  │                                       │
  └── 无法关联到同一个请求！              └── 根因排查困难
```

**分布式追踪的目标**：一条消息从发布到消费形成**完整的调用链**，无论跨多少进程。

#### 7.9.2 W3C TraceContext 传播机制

RabbitMQ.Client 7.x 内置了 `ActivitySource`，但消息的 TraceContext 需要在消息 headers 中手动传播：

```
Publisher:
  1. ActivitySource.StartActivity("order.publish")  → 创建 span
  2. 将 traceparent / tracestate 注入到 BasicProperties.Headers
  3. Publish 消息

Subscriber:
  1. 从 BasicProperties.Headers 提取 traceparent
  2. ActivitySource.StartActivity("order.consume", PropagationContext)
     → 恢复父 span 上下文，创建子 span
  3. 执行业务逻辑
  4. span.End()
```

#### 7.9.3 RabbitMQ.Client 7.x 内置 OpenTelemetry

RabbitMQ.Client 7.x 已内置 `ActivitySource`（名为 `RabbitMQ.Client`），自动为以下操作创建 spans：

| 操作 | Span 名称 | 说明 |
|------|-----------|------|
| 连接创建 | `RabbitMQ.Client.Connection.CreateAsync` | 建立 TCP 连接 |
| 通道创建 | `RabbitMQ.Client.Channel.CreateAsync` | 创建 AMQP Channel |
| 基础发布 | `RabbitMQ.Client.BasicPublish` | 发送消息（但默认不带 TraceContext 传播） |

> 注意：内置 spans 提供**客户端操作的可观测性**，**不会自动将 TraceContext 注入到消息 Headers**。跨进程链路追踪需要手动实现 TraceContext 传播。

#### 7.9.4 TraceContext 注入与提取

**发布者 — 发送时注入 traceparent：**

```csharp
public class RabbitMQPublisher
{
    private static readonly ActivitySource ActivitySource = new("RabbitMQDemo.Publisher");
    private readonly IChannel _channel;

    public async Task PublishAsync<T>(string exchange, string routingKey, MessageEnvelope<T> envelope)
    {
        using var activity = ActivitySource.StartActivity("order.publish", ActivityKind.Producer);
        if (activity is not null)
        {
            activity.SetTag("message.id", envelope.MessageId);
            activity.SetTag("exchange", exchange);
            activity.SetTag("routing_key", routingKey);
        }

        var body = serializer.Serialize(envelope);
        var props = new BasicProperties
        {
            Headers = new Dictionary<string, object?>()
        };

        // 注入 W3C TraceContext
        if (activity?.Id is not null)
        {
            props.Headers["traceparent"] = activity.Id;
            if (activity.TraceStateString is not null)
            {
                props.Headers["tracestate"] = activity.TraceStateString;
            }
        }

        await _channel.BasicPublishAsync(
            exchange: exchange,
            routingKey: routingKey,
            mandatory: true,
            basicProperties: props,
            body: body);
    }
}
```

**订阅者 — 消费时提取 traceparent：**

```csharp
public class RabbitMQConsumerService
{
    private static readonly ActivitySource ActivitySource = new("RabbitMQDemo.Subscriber");

    private async Task HandleMessageAsync(BasicDeliverEventArgs args)
    {
        // 从消息 headers 提取 TraceContext
        var parentContext = Propagators.DefaultTextMapPropagator.Extract(
            default, args.BasicProperties.Headers, ExtractTraceContext);

        using var activity = ActivitySource.StartActivity(
            "order.consume",
            ActivityKind.Consumer,
            parentContext.ActivityContext);

        if (activity is not null)
        {
            activity.SetTag("message.id", GetMessageId(args));
            activity.SetTag("exchange", args.Exchange);
            activity.SetTag("routing_key", args.RoutingKey);
            activity.SetTag("queue", _queueName);
        }

        try
        {
            await _messageProcessor.ProcessAsync(envelope, cancellationToken);
            await _channel.BasicAckAsync(args.DeliveryTag, false);
        }
        catch (Exception ex)
        {
            activity?.SetStatus(ActivityStatusCode.Error);
            activity?.AddException(ex);
            throw;  // 外层处理 basicNack → DLQ
        }
    }

    private static IEnumerable<string> ExtractTraceContext(IBasicProperties? props, string key)
    {
        if (props?.Headers?.TryGetValue(key, out var value) == true && value is byte[] bytes)
            yield return Encoding.UTF8.GetString(bytes);
    }
}
```

### 7.12 进阶主题（P1/P2 补充知识）

以下主题对生产环境有价值，但不在本 Demo 的核心实现范围内，作为扩展知识记录供参考。

#### 7.12.1 消费者取消通知（Consumer Cancellation Notification）

当队列被删除或 Exchange 被删除时，RabbitMQ 会自动取消该队列上的消费者。如果不做处理，消费者进程会无感知地进入空转状态。

```csharp
// 注册消费者取消事件
channel.ConsumerCancelledAsync += (sender, args) =>
{
    logger.LogWarning("消费者 {ConsumerTag} 已被 Broker 取消", args.ConsumerTag);
    // 根据需要：记录告警、自动重新声明队列和重新消费
    return Task.CompletedTask;
};
```

#### 7.12.2 Single Active Consumer（单一活跃消费者）

当一个队列有多个消费者实例时，默认是**竞争消费**模式（所有实例平分消息）。启用 **Single Active Consumer** 后，只有一个消费者实例实际接收消息，其他实例作为备用：

```csharp
var args = new Dictionary<string, object?>
{
    { "x-single-active-consumer", true }
};
await channel.QueueDeclareAsync("order.created.q", durable: true,
    exclusive: false, autoDelete: false, arguments: args);
```

| 场景 | 竞争消费（默认） | Single Active Consumer |
|------|-----------------|----------------------|
| 高吞吐 | ✅ 所有实例同时处理 | ❌ 只有 1 个实例处理 |
| 消息顺序 | ❌ 全局乱序 | ✅ 严格有序 |
| 高可用 | ✅ 任一挂掉，其他接手 | ✅ 主挂掉，备用顶上（更平滑） |
| 适用 | 无状态、高吞吐 | 需要严格顺序的业务（订单状态机） |

#### 7.12.3 消费者优先级（Consumer Priority）

绑定同一队列的多个消费者可以设置优先级，高优先级的消费者优先收到消息（只要它未被阻塞）：

```csharp
await channel.BasicQosAsync(0, prefetchCount: 10, global: false);
// 默认优先级为 0，设置更高的值获得优先调度
// RabbitMQ.Client 7.x：在 BasicConsume 时通过参数指定
var consumeArgs = new Dictionary<string, object?>
{
    { "x-priority", 10 }
};
```

#### 7.12.4 批量发布（Batch Publishing）

高吞吐场景下，批量发布消息可以显著减少网络往返：

| 方式 | 说明 | 吞吐量 |
|------|------|--------|
| 逐条发布 + 逐条确认 | 每条消息都等待确认 | 基准 |
| **批量发布 + 批量确认** | N 条消息连续发布，一次等待所有确认 | 通常高 3-10 倍 |
| 异步管道 | 使用 `ChannelBasicAcksAsync` 事件回调，不阻塞 | 最高 |

```csharp
// 批量发布模式
const int BATCH_SIZE = 50;
var pending = new List<(string exchange, string routingKey, ReadOnlyMemory<byte> body)>();

async Task FlushBatchAsync()
{
    foreach (var (ex, rk, body) in pending)
    {
        await channel.BasicPublishAsync(ex, rk, mandatory: true, body: body);
    }
    await channel.WaitForConfirmsOrThrowAsync();  // 一次等待所有确认
    pending.Clear();
}

// 逐条加入批次，达到阈值时刷新
pending.Add((exchange, routingKey, body));
if (pending.Count >= BATCH_SIZE)
    await FlushBatchAsync();
```

#### 7.12.5 消息生存时间（TTL）

| TTL 类型 | 设置方式 | 行为 |
|---------|---------|------|
| **队列级 TTL** | `x-message-ttl` 参数声明队列 | 队列中所有消息的超时时间，到期后进入 DLQ（如果配置了） |
| **消息级 TTL** | `BasicProperties.Expiration` | 单条消息的超时时间，精确到毫秒 |
| **队列自动删除 TTL** | `x-expires` 参数声明队列 | 队列在无消费者和消息后自动删除的等待时间 |

```csharp
// 队列级 TTL（60 秒后进入 DLQ）
var args = new Dictionary<string, object?>
{
    { "x-message-ttl", 60000 },                    // 毫秒
    { "x-dead-letter-exchange", "dlx.order" }
};

// 消息级 TTL（30 秒）
var props = new BasicProperties
{
    Expiration = "30000"                           // 字符串，毫秒
};
```

#### 7.12.6 优先级队列（Priority Queue）

允许队列中的消息按优先级排序，高优先级的消息优先被消费：

```csharp
var args = new Dictionary<string, object?>
{
    { "x-max-priority", 10 }        // 0-255，推荐不超过 10
};
await channel.QueueDeclareAsync("order.priority.q", durable: true,
    exclusive: false, autoDelete: false, arguments: args);

// 发布时设置优先级
var props = new BasicProperties { Priority = 5 };
```

> **注意事项**：优先级队列内部需要额外的排序开销，大量使用会影响性能。优先级只在队列积压时生效；如果消费者速度足够快，消息无积压，优先级没有意义。

#### 7.12.7 消息大小限制

RabbitMQ 默认消息大小限制为 **128MB**（通过 `rabbitmq.conf` 中的 `max_message_size` 配置）。实际生产建议：

- 单条消息不超过 **1MB**，大消息建议拆分为小消息或使用对象存储引用
- 超过限制的消息会被 Broker 拒绝，通道抛出异常

#### 7.12.8 流控（Flow Control）

当 RabbitMQ 的内存或磁盘达到阈值时，会自动触发**流控**（Flow Control），减缓或暂停发布者的连接：

```
收到消息 → Broker 内存/磁盘告警 → 连接进入 Flow 状态 → 发布者暂停发送
              ↓
        恢复后 → 解除 Flow
```

- 连接状态可以通过 `ConnectionBlockedAsync` / `ConnectionUnblockedAsync` 事件监听
- 配置层面：设置 `vm_memory_high_watermark`（默认 0.4 = 40%）和 `disk_free_limit`（默认 50MB）

#### 7.12.9 管理 REST API

RabbitMQ Management 插件提供 HTTP API，可用于自动化监控和运维：

```bash
# 获取所有队列信息
curl -u guest:guest http://localhost:15672/api/queues

# 获取某个队列的详细信息（含深度、消费者数、未确认数）
curl -u guest:guest http://localhost:15672/api/queues/%2f/order.created.q

# 获取连接信息
curl -u guest:guest http://localhost:15672/api/connections
```

#### 7.12.10 Trace 插件与 Firehose

用于调试消息路由问题：

```bash
# 启用 Firehose（将所有消息的发布和投递记录到 amq.rabbitmq.trace 交换机）
rabbitmqctl trace_on

# 创建一个队列绑定到 amq.rabbitmq.trace 即可查看所有消息流
# 消费该队列可以看到每条消息的发布和投递事件
```

> **生产慎用**：Firehose 会产生大量额外的消息，仅在调试阶段临时开启。

#### 集成测试：IdempotencyIntegrationTests

| # | 测试用例 | 前置条件 | 操作步骤 | 预期结果 |

// RabbitMQFixture.cs — 集成测试共享连接
public class RabbitMQFixture : IAsyncLifetime
{
    public IConnection Connection { get; private set; }
    public IChannel Channel { get; private set; }

    public async Task InitializeAsync()
    {
        var factory = new ConnectionFactory
        {
            HostName = "localhost",
            Port = 5672,
            UserName = "guest",
            Password = "guest"
        };
        Connection = await factory.CreateConnectionAsync();
        Channel = await Connection.CreateChannelAsync();
    }

    public async Task DisposeAsync()
    {
        await Channel.CloseAsync();
        Connection.Close();
    }

    // 辅助方法：声明 DLX/DLQ
    public async Task DeclareDeadLetterInfrastructureAsync()
    {
        await Channel.ExchangeDeclareAsync("dlx.order", ExchangeType.Fanout, durable: true);
        await Channel.QueueDeclareAsync("order.dlq", durable: true, exclusive: false, autoDelete: false);
        await Channel.QueueBindAsync("order.dlq", "dlx.order", routingKey: "");
    }

    // 辅助方法：声明带 DLQ 绑定的主队列

    {

        {
            { "x-dead-letter-exchange", "dlx.order" }

        await Channel.QueueDeclareAsync("order.created.q", durable: true,
            exclusive: false, autoDelete: false, arguments: args);
    }

    // 辅助方法：获取队列消息数量
    public async Task<uint> GetMessageCountAsync(string queueName)
    {
        var result = await Channel.QueueDeclarePassiveAsync(queueName);
        return result.MessageCount;
    }

### 11.6 Testcontainers 容器化集成测试

#### 11.6.1 为什么需要 Testcontainers

| 场景 | 问题 | 解决方案 |
|------|------|---------|
| **CI/CD 环境** | 没有安装 RabbitMQ 服务，集成测试无法运行 | Testcontainers 在 Docker 中自动启动 RabbitMQ 容器 |
| **本地环境** | 开发者未安装 RabbitMQ 时无法运行集成测试 | 拉起容器即可测试，无需本地安装 |
| **测试隔离** | 多个测试共享一个 RabbitMQ 实例，互相干扰 | 每个测试类使用独立容器，用完即销毁 |

#### 11.6.2 Testcontainers Fixture 设计

```csharp
public class RabbitMQContainerFixture : IAsyncLifetime
{
    private readonly RabbitMqContainer _container;

    public IConnection Connection { get; private set; }
    public IChannel Channel { get; private set; }
    public string ConnectionString => _container.GetConnectionString();

    public RabbitMQContainerFixture()
    {
        _container = new RabbitMqBuilder()
            .WithImage("rabbitmq:4.0-management")  // 带管理插件的镜像
            .WithPortBinding(5672, true)            // 随机映射 AMQP 端口
            .WithPortBinding(15672, true)           // 随机映射管理端口
            .WithUsername("guest")
            .WithPassword("guest")
            .Build();
    }

    public async Task InitializeAsync()
    {
        await _container.StartAsync();

        var factory = new ConnectionFactory
        {
            HostName = _container.Hostname,
            Port = _container.GetMappedPublicPort(5672),
            UserName = "guest",
            Password = "guest"
        };
        Connection = await factory.CreateConnectionAsync();
        Channel = await Connection.CreateChannelAsync();
    }

    public async Task DisposeAsync()
    {
        await Channel.CloseAsync();
        Connection.Close();
        await _container.StopAsync();
        await _container.DisposeAsync();
    }

    // 辅助方法与 RabbitMQFixture 相同（DeclareDeadLetterInfrastructureAsync 等）
}
```

#### 11.6.3 两种 Fixture 的适用场景

| Fixture | 前置条件 | 使用场景 |
|---------|---------|---------|
| `RabbitMQFixture` | 本地已安装 RabbitMQ 服务 | 开发者本地快速测试，无需 Docker |
| `RabbitMQContainerFixture` | 需要 Docker 环境 | CI/CD 环境、无 RabbitMQ 的本地环境 |
